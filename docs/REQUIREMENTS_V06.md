# 0.6 需求基线：Sites 真实联机与网页标识

变更依据：用户于北京时间 2026 年 10 月 18 日 15:48 要求“明天演示必须真正可以多用户、多设备交互，先借用 Site 实现真正可用的服务”，并要求“logo 改成网页的标识”。本文件补充并继承 [REQUIREMENTS_V05.md](REQUIREMENTS_V05.md) 的产品行为，替代其中 Sites 仅作静态评审的部署安排。

## 本轮交付

| 需求 | 可验收的行为 | 不能代替验收的情况 |
| --- | --- | --- |
| 共享服务 | 多个独立浏览器／设备从同一 HTTPS 地址加入同一房间，互相看到服务端已确认的状态与消息 | 仅同一 Cookie 的多标签页；各自 localStorage；预置“其他玩家” |
| 持久房间 | 刷新、断线恢复后，从服务端读取原房间、角色、聊天和举报记录 | 只在页面变量或浏览器存储里保存房间 |
| 访客入口 | 填昵称即可进入；邀请链接保留房间目标，不要求邀请码、注册、密码或 ChatGPT 账号 | 把昵称当作身份凭据；从同名恢复别人的房主权限 |
| 房间互动 | 两人开场，正文／贴纸互相可见，房主背景与公告同步，加入／选角／正式离开／移出写入历史 | 只更新操作者自己的画面；断线自动退角或重复写入入场记录 |
| 旁观与移出 | 默认旁观；舞台只读，后台不能读取；房主可移出其他人并释放角色，原会话不能重入 | 仅隐藏按钮；通过直连 API 仍能越权 |
| 网页标识 | 页面品牌标识与网页图标采用同一现有网页图形，保留可读名称和深浅主题表现 | 继续在页面和标签页使用两套互不对应的标识 |
| 接续与公开源码准备 | 同一 Git 主线保留前端、两个运行适配器、协议、测试和部署资料；区分代码、素材与私有运行数据 | 上传部署密钥／数据库；自动给第三方素材套代码许可；未经要求发布 GitHub 仓库 |

## 功能与工程范围

两团十个角色、二十个自由场所、统一的官方人物素材、全幅背景、深浅主题、手机布局、房主背景／公告、无邀请码、昵称访客、旁观、举报、移出、入退场历史和贴纸沿用 0.5 已明确的行为。贴纸消息仍不在图片下显示名称，搜索和无图回退保留可读文本。这里不重新加入剧情脚本、角色审批或假玩家。

本轮新增部署适配：共享后端运行在 Sites 支持的服务环境，以 D1 保存数据。消息传输可采用真实服务端 HTTP 同步与轮询；“多设备可用”不以 WebSocket 这个具体协议为前提，但页面必须如实呈现连接状态，不把本地动画当作远端确认。发送确认、读取、权限与游标仍走明确服务端协议。

为后续语言和架构迁移保留边界，详见 [ARCHITECTURE.md](ARCHITECTURE.md)。当前实现一个可验证的共享服务，不要求同时完成微服务拆分或把原 Python 服务删除。未来的破坏性接口、数据和域名迁移都需要独立迁移计划与验证。

## 验收顺序与证据边界

先确认部署地址实际上返回本轮后端标识、数据库结构与健康状态，再用独立会话做同房互动和权限测试。发布平台返回“成功”只证明构建已经交付，不直接证明联机行为。协议探针通过之后，继续检查真实桌面浏览器、手机、输入法、软键盘、图片与贴纸显示，以及大陆普通网络和演示现场的访问与更新延迟。

验收记录至少包含：实际 URL、版本／源码标识、部署时间、数据库结构、测试来源环境、独立会话数、消息与权限结果、失败和未验证项。自动化会话要明确标为测试，不伪称为真实用户使用量；境外容器访问成功不代表大陆用户已经可用。

## GitHub 事项

“可能开源”是工程准备要求，尚不是创建公开仓库、推送全部历史或选定许可的指令。发布前应能从同一源码导出一个不带私有运行数据和第三方美术包的版本，给出替换内容方式，并由维护者确认代码许可、贡献方式和问题报告入口。具体清单见 [OPEN_SOURCE.md](OPEN_SOURCE.md)。这些准备不阻断明天的服务部署。
